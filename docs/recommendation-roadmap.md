# Vibelo 推荐系统分阶段路线

当前目标不是做一个简单的标签网站，而是搭建一个可逐步升级到 Pinterest 类体验的深度学习推荐平台。标签、分类和属性仍然有价值，但它们只承担解释、筛选、搜索和冷启动辅助；主推荐链路优先走图片向量和用户行为。

## 阶段 1：图片站基础，已完成

目标：图片可以稳定上传、导入、浏览、搜索和互动。

- `images` 是唯一图片内容核心表。
- 正式发布接口写入 MinIO 和 `images`。
- 开发导入脚本直接写入 MinIO 和 `images`。
- 不再使用 `posts` 内容表。
- 点赞、收藏、评论、分享、浏览、热度全部来自真实交互，默认从 0 开始。

## 阶段 2：数据处理与模型特征，进行中

目标：图片入库后，既能被结构化管理，也能被模型理解。

- 基础属性：宽高、比例、文件大小、hash、主分类等保存在 `images`。
- 标签体系：`categories`、`tags`、`image_tags` 用于解释、筛选和搜索，不作为核心推荐召回。
- 视觉描述：`auto_label_images.py` 调用本地 Ollama 视觉模型生成描述、分类路径和标签。
- 图片向量：`vectorize_images.py` 调用 SigLIP2 类 embedding 模型，把向量写入 Milvus，把生成状态写入 MySQL 的 `image_embeddings`。

Java 后端不硬编码分类树、标签值或表结构。MySQL 表定义和字段变更统一放在 SQL 文件里。

## 阶段 3：向量召回推荐，当前实现

目标：先把真正的推荐主链路跑起来。

```text
图片入库 -> MinIO + MySQL images
图片向量化 -> CLIP/SigLIP/后续微调模型 -> Milvus
行为采集 -> Kafka -> user_behaviors + feed_impressions
在线召回 -> vector_recall_service.py
后端编排 -> FeedServiceImpl
前端展示 -> 首页流 / 详情页相关推荐
```

当前版本：

- 详情页相关推荐：用当前图片向量去 Milvus 找视觉相似图片，再用标签、分类、比例做相似补充。
- 登录用户首页：用最近正反馈图片的平均向量召回候选，再按向量分数、真实互动热度、新鲜度和质量字段排序。
- 游客或缺少行为时：使用真实热度、新鲜度和质量字段做冷启动。
- 前端曝光：进入首页和详情页相关推荐时批量发送打点事件，后端先写 Kafka，再由消费者异步落库。

## 阶段 4：准实时推荐缓存

目标：提升首页性能，减少每次请求都实时召回的压力。

- 后台任务按用户生成候选集，写入 `recommendation_candidates`。
- 在线请求优先读候选缓存，缓存不足时再实时向量召回。
- Kafka 作为行为事件流入口，Redis 可作为后续在线缓存层，MySQL 保留可审计结果。

## 阶段 5：排序与多路召回

目标：从“能推荐”升级到“推荐得更准”。

- 首页多路召回：用户兴趣向量、热门新图、关注作者、搜索词相关图。
- 详情页多路召回：当前图片向量相似、标签相似、分类相似、比例相似。
- 轻量排序：相似度、新鲜度、热度、作者质量、去重、内容过滤。
- 深度排序：后续引入双塔模型、Learning-to-Rank 或轻量 ranker。
- 多版本模型：通过 `model_name + vector_version` 并存，不破坏旧向量。

## 阶段 6：训练闭环

目标：把行为数据反哺模型和推荐策略。

- 收集曝光、点击、详情浏览、点赞、收藏、评论、分享、停留等日志。
- 构建正负样本，训练召回模型或排序模型。
- 对推荐结果做离线评估和线上 A/B。
- 根据模型版本逐步替换 CLIP 基线模型。

# Vibelo 公网简化发布

本文只覆盖当前架构：一台 ECS 运行 Nginx、前后端和中间件，业务数据库使用
RDS，图片使用 ECS 数据盘上的既有 MinIO。RDS/MinIO 首次迁移、数据盘初始化仍按
[公网部署与 Nginx 网关](./公网部署与Nginx网关.md)执行，不能用发布脚本替代。

本入口只用于**已经建立完整 SHA 发布基线后的日常更新/兼容回滚**。如果
`.env.public` 还没有同一完整 SHA 的 `VIBELO_BACKEND_IMAGE` 与
`VIBELO_FRONTEND_IMAGE`，应用首次发布也必须按完整手册执行；脚本会以“尚无完整 SHA
release 基线”明确拒绝，不能靠手工改脚本绕过。

## 最短安全流程

```text
本地开发与测试
  -> Git commit + push
  -> 本地构建 Backend/Frontend 各一次
  -> 导出固定 full-SHA 三文件 bundle
  -> 上传到 ECS /data/releases/<full-SHA>/
  -> ECS 只读 validate
  -> ECS 一条 deploy 命令完成导入、索引重建和分阶段更新
```

发布入口坚持以下边界：

- 应用镜像 tag 必须是完整 40 位 Git SHA，拒绝 `latest`、短 SHA 和 digest 替代；
- Windows 只使用本机已有基础镜像，以 `--pull=false` 构建；ECS 不执行镜像
  `pull`/`build`，所有启动固定为 `--no-build --pull never`；
- 不运行 `docker compose down -v`，不重建或删除 MinIO 卷；
- 不启用 `local-database`、`recommendation` profile，也不自动启用或移除 TLS；
- 发布前只读验收 bundle、主机、RDS、配置、固定 wheel 和**正在运行的 MinIO**；
  MinIO 不存在、身份/镜像/健康/回环端口/卷落点不符，或项目中运行了简化 HTTP 栈之外
  的服务时，在停站前直接失败；
- Compose 固定使用项目名 `vibelo-public` 和 ECS 本机
  `unix:///var/run/docker.sock`，调用者 shell 中的 `VIBELO_*`、`COMPOSE_*`、
  `DOCKER_HOST`/context 等变量不会覆盖 `.env.public` 或把发布导向其他 Engine；
- 当前 release 到目标 release 的 `backend/src/main/resources/db/migration` 必须无改动；
  发现新增、修改、删除或重命名 Flyway migration 时，必须改走完整数据库迁移发布；
- validate、deploy、rollback 都要求当前 release 到目标 release 的 Compose、Nginx、
  搜索重建脚本及其固定 requirements 完全一致；这会在发布前证明故障回滚仍可使用；
- rollback 还要求旧目标与最新 `origin/main` 的上述运行契约完全一致，避免旧应用镜像
  与当前实际运行配置混搭。发布与 MinIO 控制脚本始终来自受信任的最新主线，不属于
  旧应用运行契约；
- 内容定时器在搜索索引一致性窗口前停用，成功后恢复。发布中途失败时保持停用，
  由运维人员检查现场后重试或回滚。
- Git 门禁要求所有**已跟踪文件**清洁；不参与构建的个人未跟踪/ignored 文件可以保留。
  发布器始终留在最新 `origin/main`，不会执行 `git switch`、`checkout`、`reset` 或
  `clean`，因此不会读取、删除或覆盖这些个人文件，也不会在 rollback 时混用旧 helper。

## 1. Windows：提交并生成一个 bundle

先完成代码修改，在仓库根目录提交并推送：

```powershell
git status --short
git add <本次文件>
git commit -m "你的发布说明"
git push origin main
```

先做完全只读的本地门禁；它检查干净 Git、完整 SHA、Docker 和全部固定
`linux/amd64` 基础/运行镜像，不运行测试或构建：

```powershell
.\ops\public\New-PublicReleaseBundle.ps1 -ValidateOnly
```

通过后执行一次正式入口：

```powershell
.\ops\public\New-PublicReleaseBundle.ps1
```

正式入口依次运行 Backend 测试、Frontend 构建校验，随后只构建 Backend 和
Frontend 两个 commit 镜像各一次，并复用 `Export-PublicImageBundle.ps1` 导出固定
八镜像 release。默认输出目录是：

```text
%TEMP%\vibelo-public-<完整40位SHA>
```

输出目录必须恰好包含 tar、TSV manifest 和 `SHA256SUMS` 三个文件。不要把 wheel、
密码或其他文件混进去，也不要修改已导出的旧 release。

## 2. Windows：上传固定文件

先从脚本输出或 Git 读取完整 SHA，再上传三文件：

```powershell
$release = (git rev-parse HEAD).Trim().ToLowerInvariant()
$ecs = 'root@你的ECS公网IP'
$bundleDir = Join-Path $env:TEMP "vibelo-public-$release"

ssh $ecs "install -d -m 700 /data/releases/$release"
Get-ChildItem -LiteralPath $bundleDir -File | ForEach-Object {
  scp $_.FullName "${ecs}:/data/releases/$release/"
  if ($LASTEXITCODE -ne 0) { throw "上传失败：$($_.Name)" }
}
```

ECS 还必须已经有固定文件：

```text
/data/migration/search-reindex/pymysql-1.1.2-py3-none-any.whl
```

它一般只需按完整部署手册准备一次。不要在 ECS 在线执行 `pip install`。

## 3. ECS：拉取代码对象并只读校验

`git pull` 只更新源码，不会改变仍在运行的容器。每次都必须先把 ECS 工作树更新到
`origin/main` 当前提交；发布入口会再次核对，命令文字不能替代脚本门禁：

```bash
cd /opt/vibelo
git switch main
git pull --ff-only origin main
RELEASE="$(git rev-parse HEAD)"
```

先运行只读验证。它不会加载镜像、修改 `.env.public`/Git，也不会停止或启动服务：

```bash
sudo bash ops/public/public-release.sh validate \
  --release "$RELEASE"
```

也可写成 `deploy --release "$RELEASE" --dry-run`，但推荐统一使用 `validate`，避免
误把校验和正式操作混淆。

`deploy` 要求 `HEAD == RELEASE == origin/main`。`validate` 与 `rollback` 可以把旧 SHA
作为目标，但运行脚本的 `HEAD` 仍必须等于最新 `origin/main`；脚本全程不切工作树，
rollback 只切换经过验收的旧应用镜像引用。

## 4. ECS：一条命令正式更新

安排维护窗口后执行：

```bash
sudo bash ops/public/public-release.sh deploy \
  --release "$RELEASE" \
  --confirm-release "$RELEASE"
```

脚本会复用已有底层门禁完成：

1. 再次只读预检主机、RDS、`.env.public`、bundle、固定 wheel 和在线 MinIO；只读
   bundle 验收会解析 OCI config 验证应用 revision，并取得固定 MinIO 的内容 ID；
2. 在正式加载 tar 前，比较 bundle MinIO 内容 ID 与当前运行容器的实际 Image ID；同
   tag 不同内容也会失败。通过后才校验导入八个固定镜像，并离线验收/安装搜索依赖；
3. 保持最新 `origin/main` 发布器，不切换工作树；生成并校验新的 `.env.public` 候选
   文件，并在维护窗口前再次验收在线 MinIO；
4. 停用内容定时器，只停止 Gateway、Backend、Frontend、Kafka、Zookeeper、Redis、
   Elasticsearch；MinIO 保持运行，停站后再做一次同等级只读验收；
5. 依次启动 Elasticsearch，完整重建并原子发布搜索 alias；
6. 依次恢复 Redis/Zookeeper/Kafka、Backend/Frontend、最后 Gateway；
7. 验收 Gateway、Backend 和首页 feed，成功后恢复原先启用的内容定时器，并把
   `旧SHA -> 新SHA` 记录到 `/data/releases/vibelo-public-deployments.tsv`。

任何步骤失败都会非零退出，不会用 `--force` 跳过。若已经进入维护窗口，脚本故意
让内容定时器保持停用，避免恢复过程中继续写数据；终端会打印下一步回滚命令。

## 5. 明确回滚

回滚只允许选择仍保留三文件 bundle、已经验收过且镜像仍在 ECS 的完整旧 SHA。
先确认新版本没有执行无法向后兼容的数据库迁移；脚本无法替你证明业务层兼容性。

```bash
cd /opt/vibelo
OLD_RELEASE='<旧的完整40位Git SHA>'

sudo bash ops/public/public-release.sh validate \
  --release "$OLD_RELEASE"

sudo bash ops/public/public-release.sh rollback \
  --release "$OLD_RELEASE" \
  --confirm-release "$OLD_RELEASE" \
  --confirm-database-compatible
```

回滚命令执行前也要先 `git switch main && git pull --ff-only origin main`；发布器保持在
最新主线，用当前受信任控制面操作旧的固定应用镜像，不会执行旧 release 中的脚本。
当前 release、旧目标与最新主线之间的 Compose/Nginx/reindex/固定 requirements 必须
满足上述双向门禁；有差异就按完整手册回滚。通过后仍会重新执行 MinIO 只读验收、搜索
索引重建和健康检查，而不是仅重启旧容器。
不要删除当前/上一版 release 目录和镜像归档。若数据库已经不兼容，停止操作并从
RDS 备份制定恢复方案，不能用旧镜像强行覆盖。

## 6. TLS、推荐、首次发布和数据库迁移不在简化入口内

- 当前只用公网 IP/HTTP 时保持 `APP_WEB_ALLOWED_ORIGIN_PATTERNS=http://<公网IP>`；
- 域名备案和证书准备好后，按[域名备案与 HTTPS 上线](./域名备案与HTTPS上线.md)
  单独启用 TLS。简化入口检测到 HTTPS/443 会拒绝运行，避免静默降级；
- 当前小内存 ECS 继续保持 `VECTOR_ENABLED=false`、`MODEL_RECALL_ENABLED=false`、
  `MODEL_RANKING_ENABLED=false`。推荐服务升级使用独立方案，不能把 profile 临时塞进
  本发布命令；
- RDS、MinIO 初次迁移、应用尚无 full-SHA 基线的首次发布和灾难恢复仍按完整手册执行；
- 目标 release 含任何 Flyway migration 变化时，即使你认为 SQL 兼容，也不能使用本
  简化入口；先按完整流程完成数据库备份、迁移、验收与明确的应用启动顺序。
- 当前 release 与目标 release 的运行契约有差异时，任何动作都不能使用本入口；rollback
  还要求目标与最新主线一致。`--confirm-database-compatible` 只确认数据库业务兼容，
  不会也不能绕过 Compose/Nginx/reindex/固定 requirements 契约门禁。

底层命令和每一道校验的解释见 [公网部署与 Nginx 网关](./公网部署与Nginx网关.md)
与 [`ops/public/README.md`](../ops/public/README.md)。日常发布优先使用本文两个薄入口，
不要再手工复制整段 Compose 命令。

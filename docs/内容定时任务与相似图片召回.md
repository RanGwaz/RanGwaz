# 内容定时任务与相似图片召回

本文说明图片采集、生产导入、基础视觉向量化、详情页相似召回，以及在当前公网服务器上的安全部署边界。

## 先说结论

本地已经有约 128,153 个图片文件（约 43.7 GiB），RDS 业务库约有 126,945 张已发布图片。这个数量足够验证图片站的冷启动、搜索和视觉相似效果。当前详情页“不够相似”的首要原因不是图片太少，而是公网配置使用 `VECTOR_ENABLED=false`，详情页没有调用视觉向量服务。

当前 7.1 GiB ECS 也不适合同时运行在线八个容器、Milvus 三件套和 SigLIP2 CPU 推理：现有容器内存上限合计约 5.1 GiB，Milvus profile 还需约 2.25 GiB，尚未计算操作系统和 PyTorch。因此：

- 当前 ECS 可以安装轻量的“增量导入 + 搜索重建”定时器；
- 公网 timer 强制禁止浏览器采集；采集只在本地可见浏览器或明确授权的数据 API 上执行；
- 向量计算 timer 已准备好，但安装脚本会拒绝小于 15 GiB 的主机；
- 视觉召回应在升级到至少 16 GiB 或独立推荐节点后启用。

## 数据链路

```text
授权来源
  -> 本地可见浏览器运行 dataset_collector.py
  -> 本地人工检查图片
  -> 安全同步到 /data/vibelo-ingest/dataset/images
  -> import_images.py
  -> MinIO originals/thumbs + RDS images(PENDING_REVIEW)
  -> 人工/受控审核通过
  -> PUBLISHED + 后端事务提交后增量写入 Elasticsearch

搜索恢复链路
  -> /data/vibelo-ingest/state/search-dirty
  -> Elasticsearch 安全全量重建与 alias 原子切换
  -> 成功后才删除 search-dirty

图片
  -> vectorize_images.py
  -> Image Embedding
  -> 新版本 Milvus collection
  -> vector_recall_service.py:8091
  -> 后端 /feed/images/{id}/similar
  -> 视觉向量主召回 + 标签/分类辅助召回
```

双塔模型用于首页个性化候选召回，不参与当前详情页“以图找图”。详情页要先把基础 Image Embedding 和 Milvus 视觉召回接通，不能用双塔代替这一层。

## 已做的生产安全改造

### 采集器

`tools/dataset_collector.py` 现在支持本地可见浏览器和显式 `--headless`，账号密码只从 `RANGWAZ_LOGIN_EMAIL`、`RANGWAZ_LOGIN_PASSWORD` 读取，不再写死在源码里。manifest 只把本地文件仍存在、SHA256 一致且能够完整解码的记录视为已完成；缺失或损坏的文件会重新下载。

无头模式不能人工处理验证码、二次验证或风控。遇到这些情况应停止任务并回到可见浏览器，不应使用绕过手段。采集来源还必须确认授权、许可和平台规则。

本地非交互/无头模式使用 fail-closed：每个入口页、详情页及滚动完成后都会检查登录、验证码、二次验证或风控；检测到门禁或检测本身失败都会终止整轮任务。公网 timer 则更严格，安装器、预检和运行脚本三层都拒绝 `VIBELO_CONTENT_COLLECT_ENABLED=true`。单个 HTTP 响应默认最多 25 MiB，解码后最多 4,000 万像素；下载发生重定向时还会重新校验最终 URL。下载先写同目录临时文件并执行 `fsync`，再原子替换目标，既有文件必须通过 hash 和图片完整性校验后才能复用。

### 生产导入器

`tools/import_images.py` 现在：

- 只从环境变量读取 RDS、MinIO、目录和作者配置；
- 永远不会自动建表、删表或执行 `schema.sql`；
- 只引用已经存在且状态为 `ACTIVE` 的业务作者，不创建用户也不修改任何用户密码；
- 所有新增图片固定进入 `PENDING_REVIEW`，导入器没有“直接发布”开关；
- 以 SHA256 查询已入库图片，结果清单支持断点续跑；历史路径只作为提示，跳过前会重新确认当前文件是大小合规的普通文件、重新计算 SHA256 并核对数据库，同名文件被替换后会按新内容导入；Linux 路径保留大小写，`A.jpg` 与 `a.jpg` 不会共用断点状态；
- original/thumbnail object key 由完整 SHA256 确定，同一内容重试只覆盖同一对象；
- MySQL commit 的结果不确定时绝不删除 MinIO 对象，避免已提交记录变成永久 404；遗留孤儿对象以后通过独立审计回收；
- 单文件默认最多 25 MiB、最长边最多 16,384、总像素最多 4,000 万，并校验真实图片格式；
- 公网默认每轮最多尝试 500 个尚未完成的文件；已有成功结果只跳过、不占 500 个名额，避免前缀文件永久饿死后续队列；`0` 不再表示无限；
- 数据库提交明确成功，或已确认同 hash 记录存在后，才把源文件同盘原子移动到 `/data/vibelo-ingest/dataset/processed` 的 hash 文件名；提交结果不确定或导入失败时源文件仍留在 staging。这样历史文件不会在每周任务中反复 hash 和查库，断点队列也不会长期退化；
- 每个新文件开始前都会重新检查 `/data` 的 25 GiB 保留空间，跌破门禁后整轮立即停止，不会对余下目录逐个重复失败；
- 空目录是成功的 no-op，不连接 RDS/MinIO，也不会让 timer 变红；
- 只要有文件失败就返回非零退出码，让 systemd 正确记录失败；
- 输出机器可读摘要。

待审导入不会创建 `search-dirty`，也不会为 12 万存量图片触发无意义的全量搜索重建。审核通过时，后端在发布事务提交后执行单图增量索引。`search-dirty` 只用于先前失败或人工运维留下的全量修复请求：定时任务发现已有标记就重试，只有 alias 原子切换成功后才清除；Elasticsearch 失败或任务中断时标记会保留到下一轮。

### 人工审核闭环

内容 timer **只积累 `PENDING_REVIEW`，不会增加首页或搜索中的公开图片数量**。禁止 SQL 直接改状态，也禁止脚本循环、模型打分或其他方式批量自动批准。每一张图都必须由人实际查看后，单独选择 `APPROVED` 或 `REJECTED`。

公网 Compose 使用独立的 `APP_MODERATION_TOKEN`，它不进入内容任务环境。在当前只有公网 IP + HTTP 的阶段，不得从 Windows、浏览器或其他远端主机发送该 token；先 SSH 登录 ECS，再只通过 `127.0.0.1` 调现有网关 API。用静默输入避免 token 进入 shell 历史，并通过标准输入传给 curl，避免出现在命令参数中：

```bash
read -r -s -p 'Moderation token: ' MODERATION_TOKEN
echo

# 只读列出最多 50 条待审图片；根据返回的图片信息逐张人工看图。
printf 'X-Moderation-Token: %s\n' "$MODERATION_TOKEN" |
  curl -fsS --fail-with-body -H @- \
    'http://127.0.0.1/api/moderation/images?status=PENDING_REVIEW&limit=50'

# 看完一张后，只对这个明确的 IMAGE_ID 做一次决定；二选一，不要写循环。
IMAGE_ID=123
printf 'X-Moderation-Token: %s\n' "$MODERATION_TOKEN" |
  curl -fsS --fail-with-body -H @- -H 'Content-Type: application/json' \
    --data '{"status":"APPROVED","reason":"人工看图通过"}' \
    "http://127.0.0.1/api/moderation/images/${IMAGE_ID}/decision"

# 不通过时改为：
printf 'X-Moderation-Token: %s\n' "$MODERATION_TOKEN" |
  curl -fsS --fail-with-body -H @- -H 'Content-Type: application/json' \
    --data '{"status":"REJECTED","reason":"人工审核不通过"}' \
    "http://127.0.0.1/api/moderation/images/${IMAGE_ID}/decision"

unset MODERATION_TOKEN IMAGE_ID
```

`APPROVED` 的数据库事务提交后，后端通过 after-commit 单图增量写入 Elasticsearch；`REJECTED` 不公开。不要为了让新图“立刻出现”而手工创建 `search-dirty` 或执行全量重建。以后接入域名 HTTPS 后可以另行设计受控远程审核入口，在此之前 token 永远只留在 ECS 本机操作。

### 向量脚本

`tools/vectorize_images.py` 现在：

- 优先使用标准 `VIBELO_DB_*` 变量，避免旧 `VIBELO_MYSQL_*` 遮蔽正确密码；
- 后端地址可用 `VIBELO_BACKEND_BASE_URL` 配置，公网宿主机使用 `http://127.0.0.1`；
- 打开既有 collection 时校验 512 维与 COSINE metric；
- 阻止同一个 collection 混用不同模型或向量版本；
- 检查 RDS READY 数与 Milvus 实体数，空索引不会再被旧 READY 状态静默跳过；
- 只在待处理数为 0 且 RDS/Milvus 数量精确一致时原子写入完整覆盖标记；
- 完整覆盖标记额外绑定显式的 `projectionVersion`，召回服务每次读取标记时都连续校验，投影算法或 seed 变更后不能复用旧 collection；
- 任意批次存在失败时返回非零退出码。

每次换模型或重新发布都必须创建新的 `vector_version` 和 collection。示例使用：

```text
vector_version = siglip2-base-p224-d512-v2-public
collection     = vibelo_image_vectors_siglip2_base_p224_d512_v2_public
```

## 当前 ECS：安装轻量内容 timer

服务器开机且网站容器健康后再执行；停机维护或 ICP 首次备案期间不要安装或手工触发任务。

### 1. 拉取代码

```bash
cd /opt/vibelo
git pull --ff-only origin main
```

### 2. 准备 Python 环境

不要把依赖装进系统 Python，也不要在 ECS 上临时访问 PyPI。服务器重新开机后先运行 `python3 --version`，在联网的 `linux/amd64` 环境中为相同 Python 版本下载 `tools/requirements_content_jobs.txt` 的完整 wheelhouse，连同 SHA256 清单上传到 `/data/releases/content-job-wheels/`。验收清单后再创建独立 venv：

```bash
cd /opt/vibelo
python3 -m venv .venv-content
.venv-content/bin/python -m pip install \
  --no-index \
  --find-links /data/releases/content-job-wheels \
  -r tools/requirements_content_jobs.txt
```

公网内容 timer 不需要 Playwright 或 Chromium，也不允许安装后打开服务器采集。不要因为缺包就在生产机直接执行在线 `pip install`。

### 3. 安装 timer 并准备最小环境

```bash
cd /opt/vibelo
sudo bash ops/jobs/install-content-timer.sh
```

安装器会：

- 创建无登录 shell 的 `vibelo-jobs` 账号和它可写的 `/data/vibelo-ingest`；
- 从 `.env.public` 只抽取 RDS、MinIO 必需值到权限为 `0640 root:vibelo-jobs`
  的 `/etc/vibelo/content-job.env`，不会复制短信或 Token 密钥；
- 安装并启用 `vibelo-content-ingest.timer`；
- 不会立即执行采集、导入或向量计算。

安装器修改任何配置前会记录 timer 原来的启用/运行状态，并执行 `disable --now`；这样即使安装窗口里主机意外重启，也不会由旧的 enable 链接加载半套配置。若发现 `vibelo-content-ingest.service` 正在运行或处于切换状态，会拒绝安装；在环境发布开始前失败会恢复 timer 原来的 enabled/active 状态。任务树中出现任何符号链接也会拒绝迁权，并在启用 timer 前再次复查。旧 root 文件通过固定 `/data/vibelo-ingest`、`find -xdev` 和不跟随链接的逐项迁权处理，不使用会误跟随路径的 `chown -R`。既有同名服务账号还必须以 `vibelo-jobs` 为主组，且不能属于 `root`、`docker`、`sudo` 等敏感组。新的最小环境先只写候选文件，完成任务树迁权和 unit 准备后才原子发布；如果发布开始后的任何步骤失败，timer 会保持 disabled/stopped，不会自动恢复成“新环境 + 旧 unit”的混合状态，修复后必须重跑安装器。

安装器同步的秘密范围严格限制为：

```text
VIBELO_DB_HOST
VIBELO_DB_PORT
VIBELO_DB_NAME
VIBELO_DB_USER
VIBELO_DB_PASSWORD
MINIO_ACCESS_KEY
MINIO_SECRET_KEY
MINIO_BUCKET
```

可以编辑该文件里的导入批次、资源门禁、导入/搜索布尔开关和作者名，但采集开关必须保持 `false`；重新运行安装器只保留这组明确安全的调优键。仓库路径、任务路径、Python 路径、MinIO/ES 地址和媒体前缀始终恢复为审计模板值，不能通过旧环境漂移出 systemd 的 `ReadWritePaths`。安装器会同步最新的
RDS/MinIO 值。unit 不再载入 `/opt/vibelo/.env.public`，因此内容
解析进程不会得到短信 AccessKey、登录 Token 密钥等无关秘密。不要把 `.env.public`
整份复制到任务环境。安装器会先校验全部必需值，再从白名单模板一次原子替换
任务环境；旧文件中未知的变量会被丢弃。它还会将旧版 root 任务留下的
`/data/vibelo-ingest` 文件所有权迁移给 `vibelo-jobs`，避免重启后无法续写。

默认每周日 03:30 运行，并随机延迟最多 30 分钟。`Persistent=false` 表示服务器关机错过后直接跳过，不会在开机时立刻与 Elasticsearch、Kafka 抢资源。

### 4. 先保持浏览器采集关闭

确认 `/etc/vibelo/content-job.env` 中：

```text
VIBELO_CONTENT_COLLECT_ENABLED=false
VIBELO_CONTENT_IMPORT_ENABLED=true
VIBELO_CONTENT_SEARCH_REINDEX_ENABLED=true
```

把本地经过许可、已经检查的图片同步到：

```text
/data/vibelo-ingest/dataset/images
```

root 经 SCP/rsync 上传后，新文件通常会是 `root:root`。不要放宽目录到 `777`，也不要手工执行递归 `chown`。同步前先停止 timer 并确认 oneshot 不在运行；同步时禁止链接，完成后让安全安装器重新检查整个任务树并迁权：

```bash
sudo systemctl stop vibelo-content-ingest.timer
if sudo systemctl is-active --quiet vibelo-content-ingest.service; then
  echo '内容任务仍在运行，停止同步并等待任务结束' >&2
  exit 1
fi

# 从本地主机上传普通图片文件；使用 rsync 时加 --no-links，不同步符号链接。
# 上传完成后先检查：有任何输出都必须停止，不要继续。
sudo find -P /data/vibelo-ingest -xdev -type l -print -quit

cd /opt/vibelo
sudo bash ops/jobs/install-content-timer.sh
```

安装器覆盖本次新同步的 root 文件迁权，并重新启用 timer；如果任务树存在链接会直接失败。

导入后仍然只会进入 `PENDING_REVIEW`。必须通过现有审核流程明确批准，批准事务提交后后端才会增量加入搜索索引并公开展示。

然后通过 systemd 以 `vibelo-jobs` 身份加载同一份最小环境并预检。预检不仅检查 HTTP 健康，还会用内容 venv 执行 RDS `SELECT 1 / CURRENT_USER()` 和 MinIO `bucket_exists` 只读认证；失败只报告网络、认证或权限类型，不显示秘密值，也不用 root shell `source` 环境文件：

```bash
cd /opt/vibelo
sudo systemd-run --unit=vibelo-content-preflight \
  --wait --pipe --collect --uid=vibelo-jobs \
  --property=WorkingDirectory=/opt/vibelo \
  --property=EnvironmentFile=/etc/vibelo/content-job.env \
  /usr/bin/bash /opt/vibelo/ops/jobs/content-job-preflight.sh
```

首次人工验证：

```bash
sudo systemctl start vibelo-content-ingest.service
sudo systemctl status vibelo-content-ingest.service --no-pager
sudo journalctl -u vibelo-content-ingest.service -n 200 --no-pager
```

查看下一次执行时间和历史摘要：

```bash
systemctl list-timers vibelo-content-ingest.timer --no-pager
ls -la /data/vibelo-ingest/history
```

### 5. 图片采集只在本地进行

需要补充素材时，在本地可见浏览器中运行采集器，人工处理合法登录并检查来源授权、重复图和内容质量。遇到验证码、二次验证或风控就停止，不绕过平台限制。检查完成后按上一节的“停止 timer → 禁止链接同步 → 重跑安装器迁权 → 预检”流程送到公网。公网 `/etc/vibelo/content-job.env` 中的 `VIBELO_CONTENT_COLLECT_ENABLED` 永远保持 `false`。

## 升级/独立节点后：安装向量 timer

当前 7.1 GiB ECS 不执行这一节。升级到至少 16 GiB，或者准备独立推荐节点后：

1. 把 SigLIP2 Base 模型完整放到版本化的只读目录 `/data/vibelo-models/google__siglip2-base-patch16-224`；禁止在原目录覆盖模型文件，模型变更必须使用新目录、新 `vector_version` 和新 collection。当前仓库尚没有由模型发布器产出的权威文件清单/签名，因此不把“安装时现算当前目录 hash”冒充供应链验证；正式切换模型前应先由发布器产生并锁定 SHA256 清单，再把该工件身份加入安装门禁和 ready marker；
2. 创建 `/opt/vibelo/.venv-vector`，按 `tools/requirements_recommendation.txt` 安装固定依赖；
3. 启动 `recommendation` profile 的 `milvus-etcd`、`milvus-minio`、`milvus-standalone`；
4. 核对 `ops/jobs/vector-job.env.example` 使用全新的向量版本和 collection；
5. 安装 timer。安装器会分别创建 `vibelo-vectorize`（离线计算）与
   `vibelo-vector-recall`（只读召回 API）低权限用户，并通过
   `vibelo-vector-runtime` 组只共享必要的就绪标记；数据库凭据仅交给
   `vibelo-vectorize`，召回进程不会得到 RDS 密码。模型缓存限定在 `/data/vibelo-vector`。

```bash
cd /opt/vibelo
docker compose --env-file .env.public \
  -f infra/docker-compose.public.yml \
  --profile recommendation \
  up -d milvus-etcd milvus-minio milvus-standalone

sudo bash ops/jobs/install-vector-timer.sh
sudo systemctl start vibelo-vectorize.service
sudo journalctl -u vibelo-vectorize.service -n 200 --no-pager
```

安装器默认只启用向量定时器，**不会启动、也不会设置召回 API 开机自启**。
单轮默认最多处理 2,000 张；反复手工触发或等待 timer，直到日志显示
`Full vector coverage marker written`。该标记只会在 RDS 待处理数为 0、RDS READY 数与
Milvus 实体数精确相等、模型/向量版本/投影实现版本/collection 完全匹配时原子生成。
然后由安装器执行召回上线门禁：

```bash
sudo bash ops/jobs/install-vector-timer.sh --enable-recall
sudo systemctl status vibelo-vector-recall.service --no-pager
```

门禁会校验完整覆盖标记，只绑定 Docker 私有 bridge 网关的 `8091`，再从
`backend` 容器内请求 `/health`。绑定错误、索引不完整或后端不可达时会自动
停止并禁用 recall，不要手工改成 `0.0.0.0`或直接跳过安装器。门禁通过后，再将
`.env.public` 改为：

```text
VECTOR_ENABLED=true
VECTOR_SERVICE_URL=http://host.docker.internal:8091
```

然后只重建后端容器。`8091` 只供后端通过 `host.docker.internal` 访问，不在
安全组开放，也不再用 `127.0.0.1:8091` 当作生产健康检查。没有完成向量覆盖
验收前，不要提前打开开关。

## 详情页相似召回的近期修复

公网向量尚未启用时，后端仍会使用标签、主分类和比例做辅助召回。本次已经收紧这条降级链路：

- 不再把“全站已发布图片数”伪装成相似结果总数；
- 防御性排除详情页源图片；
- 候选耗尽后不再不断混入全站热门图片；
- 保留强视觉向量候选优先、元数据辅助加分的融合排序；
- 增加相似页排序、分页与 fallback 回归测试。

这能让“不相似的尾部结果”明显减少，但真正的视觉准确率仍要等 8091 + Milvus + 完整新版本 Image Embedding 上线后评估。建议届时固定一批人工标注查询图，至少统计 `Precision@12`、`Recall@48`、无效/重复率和向量覆盖率，不要只靠肉眼随机刷新判断。

## 运维命令

```bash
# 查看 timer
systemctl list-timers 'vibelo-*' --no-pager

# 手工触发轻量导入
sudo systemctl start vibelo-content-ingest.service

# 查看最近日志
sudo journalctl -u vibelo-content-ingest.service -n 200 --no-pager
sudo journalctl -u vibelo-vectorize.service -n 200 --no-pager
sudo journalctl -u vibelo-vector-recall.service -n 200 --no-pager

# 临时停止后续调度，不删除数据
sudo systemctl disable --now vibelo-content-ingest.timer
sudo systemctl disable --now vibelo-vectorize.timer
```

systemd 的 `flock` 防止同一任务重叠，`Nice`、`IOSchedulingClass=idle`、CPU/内存上限用于保护网站。内容任务以无登录 shell 的 `vibelo-jobs` 用户运行，只载入权限为 `0640 root:vibelo-jobs` 的 `/etc/vibelo/content-job.env`；日志和历史摘要不会打印密码或 AccessKey。`search-dirty` 必须保留到搜索重建成功，排障时不要手工删除它。
